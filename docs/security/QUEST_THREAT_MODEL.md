# Quest — threat model (Phase 02, G2)

Scope: `modules/quests` (authoring, publication, discovery, participation, staff sanction, export
and erasure), `modules/trust-safety` (the Phase 02 policy engine), the shared safety contract in
`packages/types/src/safety.ts`, migration `apps/api/drizzle/0002_quest_core.sql`, and the Quest
screens in the mobile app. Method: STRIDE over the trust boundaries below; every mitigation names
the code and the automated test that proves it (INT = `test/integration/quests.int.test.ts`,
E2E = `test/e2e/quest-journey.e2e.test.ts`, DB = `test/integration/database.int.test.ts`,
UNIT = unit suites).

The Identity threat model (`IDENTITY_THREAT_MODEL.md`) still governs authentication, sessions,
RBAC and account lifecycle; this document covers only what the Quest context adds.

## Assets and trust boundaries

| Asset                                                  | Classification | Boundary crossed                                                                                      |
| ------------------------------------------------------ | -------------- | ----------------------------------------------------------------------------------------------------- |
| Quest instructions and safety notes                    | PUBLIC*        | API → any eligible client (*only while PUBLISHED and age-appropriate)                                 |
| Draft Quest content (any non-PUBLISHED state)          | CONFIDENTIAL   | owner and `VIEW_QUEST_SUPPORT` staff only                                                             |
| Content hash, published hash, publish blockers         | INTERNAL       | owner only; never on another viewer's card or detail                                                  |
| Safety assessments (state, signals, policy version)    | INTERNAL       | staff support view; participants see only a badge for published content                               |
| Suspension reason, staff actor id                      | INTERNAL       | staff support view and `quest_audit_ledger`; never the owner's card                                   |
| Participation records (attempts, notes, deadlines)     | CONFIDENTIAL   | the participant; the staff support view sees a count only; owners see no participant list in Phase 02 |
| Owner identity facts (state, verified email, age band) | INTERNAL       | Identity → Quest through `ACCOUNT_FACTS`; never a table read                                          |
| Viewer country                                         | CONFIDENTIAL   | Profiles → Quest through `PROFILE_QUERY`; never returned to a client                                  |
| Quest audit ledger                                     | INTERNAL       | database only; ids, enums and reasons, never Quest text                                               |

Two boundaries matter more than the rest. First, **Quest never reads an Identity or Profiles
table**: it learns owner state, email verification, viewer age _band_ and viewer country through
ports, and the rule is machine-checked by `quests-must-not-read-identity-or-profile-tables` in
`.dependency-cruiser.cjs`. Second, **the safety decision is data, not a judgement made at read
time**: what governs a live Quest is the assessment it published with, recorded on the row.

## Abuse controls summary

Per-route throttles (per client IP, over the global limit): create Quest 20/min, update 30/min,
assessment 10/min, publish 10/min, discovery list 60/min, Quest detail 60/min, category catalogue
60/min, accept 30/min, start 30/min, completion request 30/min, over the application-wide default limit. Account-level: at most
`QUEST_MAX_ACTIVE_PER_OWNER` Quests in DRAFT, IN_REVIEW or PUBLISHED; one active attempt per
(Quest, account) enforced by a partial unique index; assessments older than
`QUEST_ASSESSMENT_MAX_AGE_DAYS` cannot be published against. Database-level: the publication CHECK,
the state, visibility, difficulty, effort, window, availability and country-format CHECKs, and
`ON DELETE RESTRICT` on every Quest foreign key so account deletion must go through the audited
erasure path.

## Residual risks (tracked)

- The Phase 02 policy engine is a deterministic lexicon, not a classifier. It is a floor: it
  guarantees that no Quest is published without _some_ decision and that obvious cases never reach
  ALLOWED, but it is evaded by paraphrase. AI-assisted classification behind the AI Gateway is a
  later phase, and may only suggest — the rule, or a human, still decides.
- There is no human approval path yet. `insertAssessment` is reached from the rule engine and from
  a staff suspension only, so a Quest routed to REVIEW_REQUIRED can leave review only by being
  edited and re-assessed, or by a later favourable machine decision about the same content. A
  moderation queue with cases, appeals and recorded HUMAN allow decisions is a later phase.
- Viewer country comes from the self-declared profile country, and the age band from a
  self-declared date of birth. Geographic and age enforcement is therefore only as strong as those
  declarations; the code fails closed where the signal is missing, but it cannot detect a false one.
- Discovery refills a page past blocked owners at most five times. A viewer who has blocked a large
  share of the owners in one window may receive a short page, and a short page ends the feed.
- Throttler storage is in-memory per replica (TD-02), so per-route limits are per instance until a
  Redis storage adapter ships. The per-owner Quest cap is a database count and is not affected.
- The participation expiry sweep runs from an operator CLI, not a scheduled worker; until one
  exists, an attempt stays STARTED past its window if the command is not run.
- Quest event payloads are constrained by their zod schemas and by review, but there is no
  catalogue test asserting that they carry no user text, as there is for the Identity events.
- Quest text moderation covers the Quest only. A participant's completion note is free text that no
  policy engine sees in Phase 02. It is not returned by any participation view; it is stored, it
  appears in the participant's own data export, and it is destroyed with the account.
