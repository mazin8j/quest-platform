# Identity & Profiles — threat model (Phase 01, G2)

Scope: `modules/identity`, `modules/profiles`, the global `AuthGuard`, the mobile auth flow and the
admin staff session. Method: STRIDE over the trust boundaries below; every mitigation names the
code and the automated test that proves it (INT = `test/integration/identity.int.test.ts`,
E2E = `test/e2e/onboarding-journey.e2e.test.ts`, UNIT = unit suites).

## Assets and trust boundaries

| Asset                                  | Classification | Boundary crossed                                     |
| -------------------------------------- | -------------- | ---------------------------------------------------- |
| Password hashes, refresh-token hashes  | RESTRICTED     | database only (never leave the API process)          |
| Access / refresh tokens                | RESTRICTED     | API ↔ client secure storage / httpOnly cookies       |
| Email, DOB, push tokens, device names  | CONFIDENTIAL   | client → API → database; email → mail provider       |
| Age band, roles, account state         | INTERNAL       | inside access-token claims / Principal               |
| Public profile (username, bio, avatar) | PUBLIC*        | API → any client (*subject to visibility and blocks) |
| Staff actions                          | INTERNAL       | admin console → API, audited                         |

## Threats and mitigations

| --- | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |

| T15 | Export abuse (I: attacker downloads victim data)                 | Verified email + permission; one request per 24 h; download only through a 15-min pre-signed URL of the owner's object; cross-account read 404                                                                                                                                                                                                                                                                                                                  | INT export                                   |

## Abuse controls summary

Per-route throttles (per client IP, `trust proxy` = 1 hop): register 5/min, login 10/min,
provider 10/min, refresh 30/min, verify 10/min, resend 3/5 min, forgot 3/5 min, reset 5/min,
deletion 3/5 min, export 3/5 min, blocks 30/min, availability 30/min, public profile 60/min.
Account-level: lockout, code attempts, session cap 20, export interval 24 h, single pending deletion.

## Residual risks (tracked)

- No MFA/passkeys for users or staff (TD-23). Staff accounts are the highest-value target; the admin console keeps no refresh token, so a staff session lasts one access-token TTL (TD-24).
- Throttler storage is in-memory per replica (TD-02) — limits are per instance until Redis storage ships.
- Breached-password check not implemented (TD-25): the deny-list covers only the most common passwords.
- Session lookup per request without cache (TD-22): acceptable at Phase 01 scale.
- Provider id_tokens are accepted for 5 minutes (`maxTokenAge`); nonce binding needs a client round-trip and is tracked as TD-30 (audit P01-11).
- Refresh-token reuse detection covers exactly one generation back (`previous_refresh_token_hash`); an older token fails without tripping the theft signal (TD-28).
- Mail delivery is a log adapter (TD-21): codes cannot reach real users until a provider is wired.
