# ADR-011 — Identity provider strategy and token model

## Status

Accepted (2026-09-06, Phase 01)

## Context

Phase 01 needs a secure account onboarding slice: registration, sign-in, sessions, devices, email verification, password recovery, and a path to Apple/Google sign-in that does not require production credentials for local development. The modular monolith (ADR-001) rules out an identity microservice; QUEST is mobile-first, so tokens live on devices and revocation must be enforceable server-side; minors and location data require that identity keys never be personal attributes.

## Decision

1. **Identity is internal and immutable.** Every account has a UUID v7 (`account.id`) generated by the application. Email and username are mutable attributes with partial unique indexes; they are never foreign keys, never identity claims. Deleted accounts keep only a SHA-256 tombstone of the email.
2. **Three aggregates, one module boundary.** AUTHENTICATION (`account_credential`, `account_identity`, `verification_code`, `auth_session`, `device`, `identity_audit_ledger`), ACCOUNT (`account`, `account_role`, `consent_record`, `account_deletion_request`, `data_export_request`) and PUBLIC PROFILE (`profile`, `interest`, `account_interest`, `privacy_settings`, `account_block`). The first two live in `modules/identity`; the third in `modules/profiles`. Identity is upstream: it drives Profiles through an exported provisioning port inside the same transaction; Profiles never imports Identity.
3. **Password authentication** with Argon2id (`@node-rs/argon2`, OWASP profile m=19 MiB / t=2 / p=1, rehash-on-login when parameters change), a shared password policy in `@quest/types` (≥ 10 chars, deny-list, no email local part), one generic failure message, per-account lockout after `AUTH_LOGIN_MAX_FAILURES` (default 10) for `AUTH_LOGIN_LOCK_MINUTES` (default 15), and timing equalisation for unknown emails.
4. **External identity providers behind a port.** `IdentityProviderPort.verifyIdToken` with OIDC adapters for Apple and Google (JWKS signature, issuer, audience checks via `jose`) enabled by configuring the client id, and a `FAKE` adapter (`fake:<subject>:<email>`) enabled only outside production (`AUTH_FAKE_PROVIDER_ENABLED`, refused by configuration in production). Provider accounts carry no password; sign-in of an unknown identity returns 404 so the client runs the register flow (DOB + consents).
5. **Token model.** Access tokens are HS256 JWTs signed with `AUTH_JWT_SECRET` (≥ 32 chars; `AUTH_JWT_SECRET_PREVIOUS` for zero-downtime rotation), 15-minute TTL, claims `sub` (account id), `sid` (session id), `roles`, `jti`, `iss`, `aud`; algorithm pinned. Refresh tokens are opaque 256-bit values, stored as SHA-256, **rotated on every use** with a generation counter; presenting a rotated-out token (kept as `previous_refresh_token_hash`) revokes the whole session (theft signal). Sessions have a sliding refresh expiry (30 days) and an absolute expiry (90 days); at most 20 live sessions per account (oldest evicted). Every request resolves the session row, so revocation (sign-out, password change, suspension, role revocation) is immediate regardless of the access-token TTL.
6. **Email verification and password reset** use six-digit codes hashed with a per-account salt, 15-minute TTL, 5 attempts, 60-second resend cooldown, delivered through a `MailerPort` (`log` adapter now; a provider adapter later; `memory` adapter for tests).
7. **RBAC.** `USER` is implicit; staff roles (`SUPER_ADMIN`, `TRUST_SAFETY_LEAD`, `MODERATOR`, `SUPPORT`, `ANALYST`, `READ_ONLY`) are an append-only ledger. A single global `AuthGuard` enforces default deny (`@Public` opt-out), lifecycle state, verified email and permissions; the admin console reuses the same vocabulary from `@quest/types`. The first `SUPER_ADMIN` is created only by the operator CLI.

## Alternatives Considered

- **Managed identity (Cognito, Auth0, Firebase Auth)** — rejected for Phase 01: data-residency and minors' data would leave the region boundary (ADR-008), pricing scales with MAU, lock-in on the most sensitive context, and the adapter port keeps the door open later.
- **Asymmetric access tokens (ES256/EdDSA)** — deferred: no second verifier exists in a monolith; HS256 with rotation is simpler operationally. Revisit trigger below.
- **Stateless access tokens without session lookup** — rejected: revocation latency of up to the TTL is unacceptable for suspension and theft response.
- **Magic-link sign-in only** — rejected for MVP: email deliverability in the launch region is unproven; password + provider sign-in with verification codes covers it and keeps the door open.
- **Username as identity key** — rejected: users rename; keys must never be personal data.

## Consequences

- Positive: revocation is immediate; secrets rotate without downtime; local development and CI need no external identity credentials; contracts are shared across clients; minors are protected by the band derived from a DOB that never leaves the context.
- Negative: one database read per authenticated request (session + account + roles) — acceptable now; a Redis session cache is the planned optimisation (BACKLOG TD-22). Argon2 costs ~50 ms CPU per sign-in.
- Operational: `AUTH_JWT_SECRET` must be provisioned in Secrets Manager per environment; rotation procedure documented in `docs/security/SECURITY_ARCHITECTURE.md`; the mailer needs a real delivery provider before public launch (TD-21).
- Security/privacy: see `docs/security/IDENTITY_THREAT_MODEL.md` and `IDENTITY_PRIVACY_CLASSIFICATION.md`.

## Revisit Triggers

- A second service must verify access tokens (→ asymmetric keys / JWKS endpoint).
- Sign-in p95 latency > 300 ms or session lookups > 30 % of database load (→ session cache).
- MFA or passkeys become a product requirement (→ WebAuthn adapter; the credential table is designed to add a second factor).
- Regulatory demand for managed identity in a specific market.
